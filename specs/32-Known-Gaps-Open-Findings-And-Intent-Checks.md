# 32 — Known Gaps, Open Findings And Intent Checks

## At a glance

| | |
|---|---|
| **What it is** | Everything that is known to be unfinished, uncertain, inconsistent or risky in the portal — so the owner can decide what to fix, what to accept, and what was actually intended. |
| **Who it is for** | The owner (Sufyan) — to prioritise fixes — and developers, so they do not "fix" something twice or treat a reported finding as confirmed when it was not re-tested. |
| **How it was built** | Nothing here is invented: each item is either something found directly in the code or docs during this review, or something reported in the review reports stored in the frontend repo under `frontend/plans/` (`be-report.md`, `fe-report.md`, `code-review-open-findings.md`, `frontend-ux-open-findings.md`). Where a review finding could not be re-tested in this read-only review, that is said explicitly. Where the current code contradicts an old finding, that is said too — some findings appear to have been fixed since the reports were written. |
| **Main code / sources** | Backend `src/` and frontend `src/` as read for files 01–31; review reports in `frontend/plans/` |
| **Success looks like** | The owner works through the intent checks at the end, marks each gap "fix", "accept" or "not intended", and this file becomes the decision record for what changes next. |

## How it works — the journey

```
Reviewer reads the code and the review reports
        ↓
Each gap is recorded with its source, its severity where the report gave one,
and whether it was confirmed in the code, not re-tested, or appears fixed
        ↓
Owner decides: fix it, accept the current behaviour, or say what was intended
        ↓
Fixes are built against the relevant spec file (28–31 carry the detail);
accepted gaps stay recorded here so they are not re-reported as new
```

## A note on method

A search for `TODO`, `FIXME`, `XXX`, `HACK` and "not implemented" across backend `src/` and frontend `src/` found no TODO/FIXME markers at all (the only matches were the word "placeholder" in UI placeholder text, email-template `{{variable}}` placeholders, and the Resend fallback key `re_placeholder`). So there is no hidden to-do list in the code to quote — the gaps below come from reading the code and from the review reports.

## Gaps found in the code

| # | Gap | What it means in plain words | Detail |
|---|---|---|---|
| 1 | **No automated tests in either repo** | Nothing checks automatically that the portal still works after a change. | No `*.test.*` files and no `qa/` folder were found in the backend or frontend repos during this review (the review reports refer to a `qa/` folder and to about 1,300 assertions, but that folder is not present in the repos as reviewed). The backend `package.json` has `dev`, `typecheck`, `db:migrate`, `db:audit`, `db:generate`, `db:seed-demo`, `db:studio`, `lint` and `format` scripts — no `test` script. The frontend has `dev`, `build`, `typecheck`, `lint`, `format` and `check` scripts, but no `test` script and no test files were found. The deploy workflow runs a frozen install and typecheck plus migrations only (backend README). |
| 2 | **No rate limit on the authenticated API** | A logged-in user can call staff endpoints as fast as they like. | The only limits found are on public routes (60 requests / 15 minutes per IP), on auth routes (15 failed attempts / 15 minutes per IP, plus the database login counters), on public submissions (3 per IP per 24 hours) and on notification streams (10 per user). Nothing in `src/index.ts` or the module route files limits how fast a logged-in user can call cases, merchants, users, configuration or dashboard endpoints. |
| 3 | **Rate limits are partly in memory and partly trust a client-controlled header** | The limits can be reset by a restart, split across servers, or bypassed by faking an IP address. | The public and auth limiters use `hono-rate-limiter`'s default in-memory store: the backend `.env.example` itself warns that multiple instances each get their own limits and that a restart resets them. `TRUST_PROXY_HEADERS` defaults to `true`, so the client IP comes from `cf-connecting-ip` / `x-forwarded-for` unless a trusted proxy overwrites them. A caller that sets `X-Forwarded-For` can rotate its apparent IP and get a fresh budget (review report M6 reproduced this: 70 public requests with rotating headers produced 0 `429` responses, versus 18 without the header). |
| 4 | **Login lockout can be used against the real user** | Knowing a username is enough to lock its owner out. | The database login guard allows 5 failed attempts per trusted device, 5 per account+IP and 15 per account per hour. Anyone who knows a username can spend that budget and lock the real user out of new devices for an hour (review report M6: 10 bad passwords locked the real user out for 15 minutes — the report's "15 minutes" does not match the 1-hour window in the current `login-guard.ts`, so the exact lockout length in the report may predate the current code). The trusted-device cookie is the only escape hatch. |
| 5 | **Resubmission links never expire** | A merchant's resubmission link works forever until it is used or cancelled. | `case_resubmission_tokens` has `consumed_at`, `consumed_reason` and `delivered_at`, but no expiry column and no expiry check was found in `case-resubmission-tokens.service.ts`. Password links expire after 24 hours (reset) or 72 hours (invite); merchant resubmission links stay valid until used, superseded or invalidated (review report L3). The same report notes the token lookup still matched a legacy plaintext `token` column; migration 0116 (`drop_resubmission_plaintext_token`) has since removed that column, so that half of L3 appears fixed. |
| 6 | **Merchant reads are not queue-scoped** | An agent restricted to one queue can still read any merchant's private details. | The merchant routes (`GET /api/merchants`, `/:id`, `/:id/overview`, `/:id/form`, `/:id/history`, `/:id/limits-mdr`) use `requireAuth` only, with no queue-access check — this was confirmed in the route file read for this spec. An agent restricted to one queue can therefore read any merchant's personal, bank and Drive details, while the same agent gets 403 on the merchant's cases (review report M1). Dashboard aggregates are likewise computed without the caller's queue scope (M2: `getDashboard(query)` receives no actor). |
| 7 | **Public responses return internal Drive identifiers** | An anonymous applicant gets back Google Drive file and folder IDs. | `POST /api/public/merchant-form` returns `googleDriveFileId`, `googleDriveFolderId` and `googleDriveWebViewLink` for private KYC files to an anonymous caller (confirmed in `src/apis/merchant-onboarding.ts` response typing and the form route's return shape), and `GET /api/public/resubmission/:token` returns the current document URL (review report L2). |
| 8 | **No expiry or size cap on comments and history** | A case page can load thousands of comments at once. | `GET /api/cases/:id/comments` and `GET /api/cases/:id/history` return every row with no pagination (review report M11 measured 5,000 comments returning 1.66 MB). Comments are also accepted on closed cases (L15). No maximum comment length beyond the database column type was found. |
| 9 | **Permanent merchant delete does Drive work inside the database transaction** | If the database fails after Drive files are deleted, the files cannot be restored. | `permanentlyDeleteMerchant` in `merchants.service.ts` runs Drive deletes before the database delete inside one transaction; a database failure afterwards cannot restore the Drive files, and a partial Drive failure aborts midway (review report M5). The code read for this spec matches that description. |
| 10 | **Post-commit failure in public resubmission can delete files the database now references** | A cleanup step may run after the save has already committed. | The review report (H4) describes the `catch` in `public-resubmission.routes.ts` running `cleanupFailedAttemptObjects` even after the transaction has committed, which deletes `current` objects as well as `provisioning` ones. | 11 | **`case_merchant_requests.token_id` has no foreign key** | The link between a merchant request and its resubmission token is not enforced by the database. | In `src/db/schema.ts` the column is a plain `uuid` with a comment ("The resubmission link the email carries") and no `references(...)` clause, unlike the neighbouring `email_log_id` and `release_stage_id` handling. | 12 | **The Resend client is built with a placeholder key when email is not configured** | A missing email key is only noticed when an email is actually sent. | `getResendClient()` uses `env.RESEND_API_KEY ??
